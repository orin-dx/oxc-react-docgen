[MEDIUM] JSDoc consumption ordering bug — surfaced while reviewing the &mut self cascade (mission item #5); it's a real, reproducible hazard, and arguably its own #6-adjacent silent-mis-attribution bug
— crates/core/src/extractor/visit.rs:113-139 (`visit_ts_interface_declaration`) + jsdoc.rs:15-37 (`find_jsdoc`)
```rust
fn visit_ts_interface_declaration(&mut self, node: &TSInterfaceDeclaration<'a>) {
    ...
    let props: Vec<RawProp> = node.body.body.iter().filter_map(|sig| self.collect_property_signature(sig)).collect();
    //  ^ each prop's find_jsdoc(prop.span_start) runs FIRST, marking whatever comment it finds "consumed"
    let description = self.find_jsdoc(node.span.start);
    //  ^ interface's OWN comment is claimed LAST
```
`find_jsdoc` marks the returned comment consumed (`consumed_jsdoc.insert(span_end)`) and filters consumed comments out for all later callers. Because props are processed before the interface's own description, for `/** Props for Button. */\ninterface ButtonProps {\n  variant: string;\n}` (first prop has no comment of its own, and the interface-level comment is well within the 120-byte PROXIMITY_THRESHOLD of `variant`'s span_start — true for any short interface), `collect_property_signature`'s find_jsdoc call for `variant` runs first, claims the interface's own leading comment as the *prop's* description, and consumes it — so when `find_jsdoc(node.span.start)` runs afterward, the comment is gone and the interface's `description` comes back empty. This inverts the exact behavior the docstring above `find_jsdoc` claims to guarantee ("prevents prop JSDoc leaking into component descriptions") — here it leaks the other direction, silently, with zero diagnostic (this subsystem has no diagnostics sink at all).
On the &mut self design itself: switching `consumed_jsdoc: FxHashSet<u32>` to `Cell`/`RefCell` (interior mutability) would NOT fix this — the bug is about call *order* between sibling methods, not how the set is stored. Real fix: reorder so the parent's own `find_jsdoc(node.span.start)` runs before descending into `props` (parent-before-children), which is a 2-line swap regardless of storage mechanism.

Error handling — clean: zero `Result<_, String>` anywhere in the three crates, no stringly-typed errors. Core's extraction path doesn't use `Result` at all — it's designed to always produce a best-effort output plus `Diagnostic`s, which is the right architectural shape for "never fail silently" (when it's actually followed). CLI-level `miette` usage (`.into_diagnostic()`, `.wrap_err`) is idiomatic.

Default derives — no red flags found (global.rs:17,30; collected.rs:472; output.rs:565) — all on accumulator/stats types where a zero/empty default is semantically correct, not masking a required field.

matches! usage — the vast majority are either test assertions or string-literal membership checks (`matches!(bare_name, "FC" | "FunctionComponent" | ...)`) where there's no project enum to be exhaustive over — matches! is the correct idiom there, a full match would need a meaningless `_ => false`. A handful are single-variant filter predicates on project enums (resolver/primitives.rs:19,53,55; resolver/chain.rs:280; resolver/alias.rs:203) — fine, these are narrowing checks inside `.filter()`/`.any()`, not full dispatch. The resolver's central dispatcher, `resolve_collected_type` (resolver/collected.rs:36-145), IS a genuinely exhaustive `match` over `CollectedType` with no top-level wildcard — correctly follows the project's own rule, and is a good contrast case against the extractor's silent-None problem: `Conditional`/`Mapped` degrade to `PropType::Opaque{reason}` (good, visible in output) but — minor inconsistency — don't also push a `Diagnostic` the way `MaxDepthExceeded` and `TemplateLiteralOpaque` do a few lines above/in template.rs; worth normalizing but not a silent failure since the Opaque reason is visible per-prop in the JSON either way.

=== VERDICT ===
The codebase lives up to its own standards well wherever they're mechanically enforceable: the pub/pub(crate) module boundary is followed to the letter, there are zero stringly-typed errors, and non-test `unwrap()`/`panic!()` is nearly absent (4 hits total, 3 of which are provably-safe-today landmines rather than live bugs). It falls short precisely on the rule it repeats most emphatically across three CLAUDE.md files — "Always emit Diagnostic when degrading, never fail silently" — which the *resolver* phase honors consistently (every Opaque degradation is visible, most paired with a Diagnostic) but the *extractor* phase's component-detection and type-alias-classification code does not honor at all: one function (`extract_type_name_from_type`) fans out to 5 call sites, and its silent `_ => None` erases entire components — not just degraded props — from the output with zero trace. That this is a known gap rather than an oversight is evidenced by two dead `DiagnosticCode` variants (`ComponentDetectionFailed`, `BarrelResolutionFailed`) sitting unused in the enum, seemingly reserved for exactly this scenario and never wired up. A second, independent silent-failure path exists at the watch-mode CLI/core boundary, where real diagnostics are computed and then discarded twice — once by the CLI, once by `WatchSession::snapshot()`'s hardcoded empty vec — with a test that locks in the empty-diagnostics behavior as intentional. None of these are large fixes (one diagnostic push, one field threaded through, one two-line reorder in the JSDoc visitor), but collectively they show the project's flagship non-negotiable is currently more aspirational than enforced.
