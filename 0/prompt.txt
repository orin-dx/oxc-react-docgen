### How it hooks into Vite (`src/index.ts:15-165`)

`oxcReactDocgen(options)` returns a single `Plugin` object (not `Plugin[]`) with a closure holding mutable state: `sessionId`, `root`, `command`, `resolvedSrcDirs`, `currentOutput` (the in-memory `ExtractionOutput`, seeded with a zero-value placeholder), and `initPromise`.

Hook sequence and responsibilities:
- **`configResolved(config)`** (`src/index.ts:70-74`) — captures `root`/`command`, resolves `srcDirs` to absolute paths (`root + '/' + dir` unless already absolute), and calls `napi.createSession(napiOptions())` synchronously to get `sessionId`. No try/catch here.
- **`buildStart()`** (`src/index.ts:77-84`) — build-mode-only cold extraction. Guards on `command !== 'build'` and returns early otherwise. Calls `coldExtract()` inside try/catch, logs on failure via `console.error`. Added later (commit `62ff336`) specifically because Vite never calls `configureServer` during `vite build`, so without this the virtual module always resolved to the empty placeholder in production builds.
- **`configureServer(server)`** (`src/index.ts:86-112`) — dev-mode cold extraction. Fires `coldExtract()` fire-and-forget (`.then()/.catch()` chain, deliberately not `await`ed since `configureServer` must return its teardown function synchronously — documented at `src/index.ts:90-93`). On success, sends an `oxc-react-docgen:ready` HMR event via `server.environments.client.hot.send`. Returns a teardown closure that calls `napi.closeSession(sessionId)` — added in commit `49b12c6` to fix a dev-server session leak (comment: "`buildEnd` isn't called in dev mode — this is the only reliable cleanup hook", `src/index.ts:108`).
- **`hotUpdate(opts)`** (`src/index.ts:114-150`) — per-file-change HMR hook. Reads `(this as any).environment`, bails if absent or `env.name !== 'client'` (skips SSR). Bails if `!isSrcFile(opts.file)`. Awaits `initPromise` if set (so incremental calls queue behind the in-flight cold extraction). Calls `napi.extractFileIncremental(file, sessionId, napiOptions())`, parses the JSON result (with a try/catch fallback that logs and sends an empty update on parse failure), merges `updatedComponents` into `currentOutput.components` by `displayName` key, and sends `oxc-react-docgen:update` over HMR. Explicitly returns `undefined` (not `[]`) so Vite/React Fast Refresh still processes the file — documented at `src/index.ts:148-149`.
- **`resolveId`/`load`** (`src/index.ts:152-159`) — implements a `virtual:oxc-react-docgen` module (`\0`-prefixed per Vite convention) that serializes `currentOutput` as `export default {...}`.
- **`buildEnd()`** (`src/index.ts:161-163`) — closes the NAPI session; this is the build-mode cleanup counterpart to `configureServer`'s teardown.

`isSrcFile(file)` (`src/index.ts:63-65`): `(file.endsWith('.tsx') || file.endsWith('.ts')) &amp;&amp; resolvedSrcDirs.some(dir =&gt; file.startsWith(`${dir}/`))`.

### NAPI boundary contract (from `packages/napi/binding.d.ts`, `packages/napi/index.d.ts`, and the Rust-side semantic-model doc at `.claude/semantic-model/napi-binding.md`)

The plugin calls exactly 4 of the 5 NAPI entry points (never `extractAll`, which is the CLI's cold one-shot path):
- `createSession(options) -&gt; number` — sync
- `initializeSession(sessionId, options) -&gt; Promise&lt;string&gt;` (JSON of `ExtractionOutput`)
- `extractFileIncremental(filePath, sessionId, options) -&gt; Promise&lt;string&gt;` (JSON of `IncrementalUpdate`)
- `closeSession(sessionId) -&gt; void` — sync

Per the Rust-side doc, all five entry points are wrapped in `contain_panic` (ADR 0005) so a Rust panic can never crash the host Node process — it always surfaces as a rejected promise / thrown `napi::Error`. This means the plugin's `napi.*` calls *can* legitimately reject/throw for real reasons (bad `reactVersion`, malformed `extraPathsJson`/`knownTypeOverridesJson`, a genuine internal panic converted to an error) — not just theoretical concerns.

## Prioritized Gaps / Risks (grounded in source, with citations)

**P1 — Dev-server session-leak regression has zero test coverage**
`configureServer`'s returned teardown function (`src/index.ts:109-111`, `napi.closeSession(sessionId)`) exists specifically because of a real bug fixed in commit `49b12c6` ("session leak"). None of the 18 tests invoke the function that `configureServer` returns — test #6 (`configureServer` describe block, `plugin.test.ts:86-98`) only asserts `initializeSession` was called; it never captures or calls the returned teardown. A regression here (e.g., someone refactors `configureServer` and forgets to return the teardown, or breaks the closure over `sessionId`) would not be caught by the suite.

**P1 — `hotUpdate`'s malformed-JSON fallback path is untested**
`src/index.ts:130-136`: if `napi.extractFileIncremental` resolves to unparsable JSON, the code catches it, logs via `console.error`, and sends `oxc-react-docgen:update` with `updatedComponents: []` and `diagnostics: []` — a real fallback contract (clients should still receive *an* event rather than an unhandled rejection). No test mocks `extractFileIncremental` to return bad JSON and asserts this fallback fires. Same class of gap for `coldExtract`'s JSON.parse failure (`src/index.ts:54-60`, returns `false` and logs) — no test drives `initializeSession` to resolve with malformed JSON.

**P1 — `initPromise` gating (the queue/replay race-guard) is never actually exercised as a race**
`src/index.ts:126`, `if (initPromise) await initPromise` — this is the mechanism described in the archived spec (`docs/archive/10-PLUGIN-SPEC.md:168`, "If `configureServer` is called before `initializeSession` resolves ... the `hotUpdate` handler queues updates and replays them") as the fix for a real ordering hazard: a file-change event arriving while cold extraction is still in flight. Every current `hotUpdate` test calls `hotUpdate` directly without ever calling `configureServer` first, so `initPromise` is always `null` in every test (`plugin.test.ts:39-44` `beforeEach` only calls `configResolved`, never `configureServer`) — the `await initPromise` branch's actual blocking behavior (does a `hotUpdate` call really wait for a pending cold extraction rather than racing it?) is not verified anywhere.

**P2 — Uncaught/unguarded `napi.createSession` throw in `configResolved`**
`src/index.ts:73`, `sessionId = napi.createSession(napiOptions())` is unguarded by try/catch, unlike `buildStart`/`configureServer` which both wrap their NAPI calls. Per the Rust-side contract (`.claude/semantic-model/napi-binding.md`, Invariant 2), `createSession`/the underlying `TryFrom&lt;JsExtractOptions&gt;` conversion can legitimately reject on a bad `reactVersion` value reaching the boundary (e.g. via a `reactVersion` value that bypasses the TS union type through an `as any` cast, or a future option that gains validation). A throw here happens synchronously inside `configResolved`, with no catch/log anywhere in the plugin — behavior on this path (does Vite's config-resolution abort cleanly, what message does the user see) is completely unexercised by any test.

**P2 — Trailing-slash / already-slash-terminated `srcDirs` produces a double-slash prefix that silently excludes all files**
`src/index.ts:72`, `resolvedSrcDirs = options.srcDirs.map((d) =&gt; (d.startsWith('/') ? d : `${root}/${d}`))`, combined with `isSrcFile`'s `file.startsWith(`${dir}/`)` check (`src/index.ts:64`). If a caller passes `srcDirs: ['src/']` (trailing slash) or an absolute dir already ending in `/`, the resolved dir keeps its trailing slash, and the `isSrcFile` check then tests for a *double* slash (`.../src//`) which no real file path will ever match — every file under that srcDir would be silently skipped by `hotUpdate` with no error or log. This is inferred directly from the string-concatenation logic, not from a runtime observation, but no test exercises a trailing-slash `srcDirs` entry either way, so this either is a real bug or is an untested-but-intentional footgun — either way it's unverified.

**P2 — No integration-tier tests against a real Vite dev server / real NAPI binary**
Confirmed by direct file listing: only `tests/unit/plugin.test.ts` exists; `tests/integration/` (called for in `docs/archive/10-PLUGIN-SPEC.md:181-186`, gated by `NAPI_BINARY_AVAILABLE`, `pool: 'forks'`) was never implemented. Everything the unit suite verifies is really "the plugin calls the mocked NAPI functions with the right arguments and wires their (mocked) return values to the right Vite hook outputs" — it says nothing about whether the actual generated `.node` binary's real JSON shapes match what the plugin expects, whether a real Vite `HotUpdateOptions`/`ViteDevServer` shape matches the plugin's assumptions (e.g. the `(this as any).environment` cast at `src/index.ts:119`, or `(server as any).environments?.client?.hot?.send` at `src/index.ts:99` — both defensive casts specifically because the real Vite API surface across 6/7/8 patch versions isn't type-checked here), or whether the plugin behaves correctly through a real HMR file-save cycle. `docs/STATUS.md:5`'s "fully tested" claim is not supported by what actually exists on disk.

**P3 — Concurrent/out-of-order `hotUpdate` calls for the same file are not addressed or tested**
`src/index.ts:138-139`, `for (const comp of update.updatedComponents) { currentOutput.components[comp.displayName] = comp }` — there is no sequencing/versioning guard. If Vite fires `hotUpdate` twice in quick succession for the same file (e.g., an editor auto-save plus a formatter re-save, or a git checkout touching many files), and the two `extractFileIncremental` calls resolve out of order, the *older* result could overwrite the newer one in `currentOutput.components`, and the correspondingly stale `oxc-react-docgen:update` HMR payload would be sent after the fresher one. No stats/timestamp/sequence check exists to detect or prevent this, and no test constructs two overlapping `hotUpdate` calls to check ordering.

**P3 — `.d.ts` files match `isSrcFile`'s `.ts` suffix check with unclear intent**
`src/index.ts:64`, `file.endsWith('.tsx') || file.endsWith('.ts')` — a changed `foo.d.ts` file also ends in `.ts`, so if it's inside `srcDirs` it will trigger a full `extractFileIncremental` call treating the declaration file as an extraction target. There's no test (or comment) establishing whether this is intended (ambient types affecting prop resolution) or an oversight; either way it's unverified behavior.

**P3 — `buildEnd`/`configureServer`-teardown interplay under `vite build --watch` is unaddressed**
The comment at `src/index.ts:108` states "`buildEnd` isn't called in dev mode — this is the only reliable cleanup hook," implying the two cleanup paths (`configureServer` teardown for serve, `buildEnd` for build) are mutually exclusive. `vite build --watch` is a build-mode long-running watch process where Vite's own hook-calling semantics around repeated `buildEnd` invocations aren't verified against this plugin's single-session-per-`configResolved` model (`sessionId` is set once in `configResolved`, and `buildEnd` unconditionally calls `closeSession(sessionId)` — a second rebuild in watch mode would call `buildEnd` again against an already-closed or newly-needed session). No test or comment covers this mode.

**P4 — Options forwarding beyond `srcDirs`/`htmlAttributes` is largely unasserted**
Tests consistently use `expect.objectContaining({ srcDirs: [...] })` (e.g. `plugin.test.ts:80,96,122,187`) or `htmlAttributes` alone; `exclude` and `reactVersion` are declared in `OxcDocgenOptions` and threaded through `napiOptions()` (`src/index.ts:39-46`) but no test ever passes non-default `exclude`/`reactVersion` values and asserts they reach the NAPI call. Low risk (simple pass-through) but literally unverified.</result>
