## What "SDD" actually is

Not formally named "SDD" anywhere in the repo — the README calls it "Nine cooperating plugins covering the full development lifecycle, connected by shared JSON schemas and a common verification gate." The stated problem: agents working across long sessions silently drop acceptance criteria as context compresses. Specs live on disk (not just in conversation context); agents are required to read from disk (`spec_file_path`); drift becomes detectable instead of silent. Core mechanism is schema-typed handoffs, not prose descriptions of what the next agent expects.

Four load-bearing design decisions (see ARCHITECTURE.md §Design Principles and docs/adr/001-005):
1. **Schema-Driven Development** — every inter-agent handoff is a JSON Schema draft-2020-12 doc in `shared/schemas/`, `additionalProperties: false`, validated at wiring time (before an agent acts on it, not at runtime inside the agent). Versions are immutable: a breaking change creates `<name>@2.json`, never mutates `@1`. Every schema carries a `reasoning: string` scratchpad field that is generated but never forwarded downstream (keeps chain-of-thought out of consumers).
2. **EARS output contracts** — WHEN/IF/WHILE/WHERE/THE SYSTEM SHALL notation is *restricted to* each agent's `<output>` section (hard constraints only). ADR-002's rationale: EARS everywhere caps the agent at the author's imagination — the "interior" (backstory/goal/judgment, i.e. how it searches and reasons) must stay unconstrained prose so the agent's judgment can generalize past what the author anticipated.
3. **4-part agent structure** (ADR-001) — every agent body is exactly `<backstory>` (2-4 sentences of experiential perspective/what it's been burned by, replaces a `<role>` label), `<goal>` (intent not steps), `<judgment>` (the specific failure mode that looks like success — replaces generic success-criteria checklists), `<output>` (schema ref + EARS). No other body sections permitted; `basis-auditor` mechanically checks for violations (stray `<role>`, `success_criteria`, EARS outside `<output>`).
4. **Cognitive mode separation** (ADR-003) — agents are dispatched by *mental mode required*, not pipeline position: enumeration (haiku/low — recon, scanners, mechanical completeness, must NOT filter/judge), analysis (sonnet/medium — drafting, scanning-then-reasoning), adversarial (opus/high — default-to-skepticism, requires a concrete failing scenario to confirm anything), judgment (opus/high — exit gates, binding verdicts). Rationale: a scanner that also filters "because a match looks harmless" creates false negatives the next agent can never recover, and an adversary forced to also enumerate loses depth. So every plugin with N cognitive phases has N agent files, never one agent doing two modes.

## The "semantic model" question — direct answer

There is **no separate semantic-model / architecture-model artifact type**. I grepped the whole repo for "semantic model", "domain model", "architecture model", "system model" — the only hits are in `plugins/canon/agents/canon-drafter.md`, `canon-auditor.md`, and `canon/CHANGELOG.md`. "Semantic model" here names a **quality bar for acceptance criteria inside a spec@1**, not an architectural artifact:

> The semantic-model anti-pattern: a criterion that sounds concrete but encodes an implementation assumption. "The deduplication logic handles collisions correctly" is not a criterion — it's a task description. "When two records with the same key are inserted, the second insert returns an error and the first record is unchanged" is a criterion. Test: could two developers with zero knowledge of the implementation evaluate the criterion identically from observable behavior alone? If not, it fails.

So: specs do **not** reference or get validated against any codebase-wide architecture/domain-model artifact. The "semantic model" concept is entirely about how one spec's acceptance criteria are internally worded — black-box observable behavior only, never internal state or implementation mechanics. If you want an actual architecture/domain-model artifact type (entities, module boundaries, dependency graph) for oxc-react-codegen, that doesn't exist in this methodology yet — it would be a net-new schema you'd design (the `basis/schema` sub-skill via `basis-schema-designer` is literally built for adding new `shared/schemas/*.json` types, and checks for field-name conflicts against existing schemas first).

The closest thing to "architecture as an artifact" is `canon-architect` (opus/high): given a `finding-report@1` from `proof` (the bug-hunt plugin), it doesn't patch instances — it designs a structural fix (new abstraction boundary, trait/type redesign, invariant) whose acceptance criteria must be falsifiable at the type/compiler level, e.g. `#[deny(unused_variables)]` on a destructure so a dropped field is a compile error, not a convention. Its `<judgment>` failure mode: "documentation masquerading as architecture" — "callers must ensure X is not nil" is a convention, not a fix; the test is whether a future dev following normal patterns could reintroduce the bug without a compile/test failure.

## The 9 plugins, exact pipeline, and schema

```
graph(need) --requirement@1--> trace(research) --research-report@1--> canon(spec) --spec@1--> vector(plan) --plan@1--> lambda(code) --changeset@1--> delta(ship)
                                                                          ^                        |
axiom(gate, cross-cutting) <--spec@1/changeset@1-- canon & lambda ------>|                        v (iterate)
proof(audit, cross-cutting) --finding-report@1--> delta, and --> canon-architect (structural remediation loop back into canon)
basis(meta) -- scaffolds new plugins, not part of the lifecycle graph
```

**graph** (need → `requirement@1`): `graph-intake` (sonnet/med) converts free text to a draft, inferring what it can, asking zero questions, leaving gaps in a `reasoning` scratchpad. `graph-clarifier` asks exactly one targeted question if `done_when` criteria are untestable, then populates `out_of_scope` (deliberately left empty by intake — that's clarifier's job). `graph-auditor` (sonnet/med, read-only) cross-references all open requirements against existing specs/plans/impl files in the workspace and flags covered/partial/missing/duplicate. Default backing store is GitHub Issues with a machine-readable `requirement@1` block; swappable for Jira/Linear as long as they emit the same schema.

**trace** (research → `research-report@1`): `trace-recon` (haiku/low) maps *where* answers live (doesn't read content) → `trace-reader` (sonnet/med) reads each source, extracts findings with citation + confidence (`confirmed`/`likely`/`assumed`) → `trace-risk-assessor` (sonnet/med, optional) → `trace-synthesizer` (sonnet/med) produces the report with an explicit-confidence, falsifiable `recommendation` and never resolves contradictions by picking a side without evidence.

**canon** (spec → `spec@1`), sub-skills: `canon/draft` (canon-drafter, sonnet/med) → `canon/verify` (canon-verifier, sonnet/med — grounds each criterion in the source requirement/research, classifies supported/unsupported/overfitted, no verdict) → `canon/audit` (canon-auditor, sonnet/med — adversarial hunt for untestable language, ambiguity, missing error cases) → `canon/gate` (canon-exit-gate, opus/high — binding pass/fail, default-fail disposition). On pass, the *orchestrator* (not the gate) writes the spec to `.claude/specs/<id>.json`, commits it, sets `spec_file_path`, and only then hands to vector — an uncommitted spec is defined as "not persisted." Two more sub-skills exist beyond drafting: `canon/drift` (canon-drift-checker, opus/high, **not a blocking gate** — an on-demand post-ship health check that re-reads spec-from-disk + current code and classifies each criterion covered/uncovered/drifted; explicitly refuses to trust prior `criteria_evidence` pointers or code comments claiming coverage — re-verifies every pointer itself) and `canon/architect` (described above) and `canon/correct` (revises a gated spec when `lambda-implementer` reports a criterion contradicts observed reality — overwrites the same file path, sets `revision_note`, re-enters verify→audit→gate, then routes to vector in amend mode). Constitution rule: the same criterion hitting `spec_contradiction` twice escalates to a human rather than looping canon/correct again.

**vector** (plan → `plan@1`): `vector-planner` (sonnet/med) decomposes into tasks — every task ≤15 min, exact file paths, exact TDD steps (failing test → exact command+expected-failure-output → minimal impl → verify command → conventional commit message), `covers_criteria` linking to spec acceptance-criteria IDs, propagates `spec_file_path`/`spec_hash`/`linked_requirement`. "No placeholders rule": "implement as appropriate" is treated as an abdication, not a step. `vector-estimator` (sonnet/med) adds per-task minute estimates + parallelizability + blocking deps. `vector-challenger` (opus/high) adversarially checks 6 dimensions: criteria with no task, wrong task order (references symbols not yet produced), over-specified steps, under-specified steps (implementer must make a design call), tasks >15min, spec error-cases with no test step. Runs on amended plans too — amendment isn't exempt.

**lambda** (code → committed code + `criteria_evidence`, no schema of its own for the changeset — that's delta's job): `lambda-recon` (haiku/low) detects language/test-runner/build-tool, **runs the full suite first and refuses to produce a manifest if baseline is already red**. `lambda-implementer` (sonnet/med) does one task's full TDD cycle; red phase is mandatory — a test that passes before implementation is treated as a broken test, not success. `lambda-mutator` (sonnet/med) runs cargo-mutants/Stryker scoped to the task's changed files after each commit; surviving mutants get turned into precision tests fed back to the implementer before the next task starts. `lambda-reviewer` (sonnet/med) does scope/non-negotiables/sibling-gap/test-quality review post-mutation-gate. `lambda-exit-gate` (opus/high) runs the axiom protocol independently against the spec **read fresh from `spec_file_path` on disk** (a spec with no `spec_file_path` is a hard block), assumes incompleteness, confirms mutation testing ran or was noted unavailable. Context-management rules are explicit and strict: never pass the full plan@1 or full spec@1 content on every task invocation (measured cost: "a 40-task plan passed 40 times consumes 320K–600K tokens") — pass only the current task + workspace manifest + `spec_file_path` + this task's precision tests; pass commit SHAs, not prior full results.

**axiom** (gate, cross-cutting, reusable — `plugin.json` declares `consumes: []`, nothing auto-invokes it): 3 agents in strict sequence — `axiom-recon` (haiku/low, pure inventory, no judgment) → `axiom-verifier` (sonnet/med, neutral evidence collector — classifies each criterion verified/failed/**unverifiable**, and "absence of a counter-example is not sufficient to classify verified") → `axiom-exit-gate` (opus/high, binding verdict; unverifiable criteria count as failures unless the caller explicitly waives them; pass requires zero unresolved failures). Retry protocol: on fail, orchestrator forwards *only* the `blockers` array back to the producer, not full context (constitution rule, ADR-005) — effort escalates at retry 2, circuit breaks and escalates to a human after retry 3. Note per ARCHITECTURE.md §3: `canon-exit-gate` and `lambda-exit-gate` are separate dedicated agents implementing the *same* recon→verify→judge discipline independently — they don't call into axiom's own agents; axiom is there when you want that protocol as a standalone second opinion against any artifact type.

**delta** (ship → `changeset@1`/`release-artifact@1`): `delta-commit-analyzer` (haiku/low) writes commit messages explaining *why*, not what (diff already shows what). `delta-changeset-analyzer` (sonnet/med) — if lambda's run produced `criteria_evidence`, delta uses those exact file/line pointers instead of reconstructing approximate ones from the diff; detects breaking changes; maps `acceptance_criteria_met`. `delta-pr-narrator` (sonnet/med) writes from "what does a reviewer with zero context need to approve confidently." `delta-review-preprocessor` (haiku/low) triages incoming review comments into must-fix/suggestion/question. `delta-release-summarizer` (sonnet/med) aggregates changesets into `release-artifact@1`, filters out internal-only chore/refactor entries, computes semver bump.

**proof** (audit, cross-cutting, independent of the main pipeline — "typically run before a release"): 5-phase — `proof-recon` (haiku/low, builds live/dead file manifest by tracing reachability from entry points; **proof only ever reports bugs in live/reachable code**) → `proof-scanner` (sonnet/med, loads `shared/references/rust-hazards.md` or `typescript-hazards.md`, taxonomy T1–T10, grep-pattern based, emits `candidate@1`, must NOT filter or judge) → `proof-boundary-tracer` (sonnet/med, **conditional**, only dispatched for T7/Write-Only-Fields and T10 candidates, traces every struct field to see if it reaches an execution boundary, emits `field-survival-map@1`) → `proof-adversary` (opus/high, one candidate at a time never batched, default assumption is "refuted," confirms only with a concrete failing scenario) → `proof-exit-gate` (opus/high, re-reads code fresh post-remediation, checks sibling functions with the same pattern, confirms compile+tests, escalates after 3 retries). Findings route to `delta` and, when the fix is structural, to `canon-architect` (the proof→canon loop).

**basis** (meta, not in the lifecycle graph): `basis-scaffolder` (sonnet/med) generates a full compliant `plugins/<id>/` directory on the first try. `basis-auditor` (sonnet/med, read-only) checks 7 conformance categories mechanically — e.g. flags a check with `status: pass` but empty `detail` as an assumed-not-verified pass. `basis-schema-designer` (sonnet/med) designs new `shared/schemas/*.json` for a described artifact, checks field-name conflicts against existing schemas first. Key conventions worth reusing directly for your Rust work: "Pull over inject" (agents get a workspace path + goal, discover the rest via tools — don't pre-stuff context), "Minimum viable prompt" (body target <200 words; if it reads like a numbered tutorial it's procedure masquerading as guidance), tool-count cap of 8-15 per agent ("above 20, selection accuracy degrades").

## Full schema field list (all in `shared/schemas/`, draft-2020-12, all `additionalProperties:false`, all carry a `reasoning: string` scratchpad not forwarded downstream)

- **requirement@1**: required `id, statement, stakeholder, why, done_when[]`; optional `out_of_scope[], priority(enum critical/high/medium/low), linked_issues[]`.
- **research-report@1**: required `question, findings[], recommendation, confidence(enum high/medium/low), open_questions[]`; each finding: required `claim, evidence, confidence(enum confirmed/likely/assumed)`, optional `source`; optional `linked_requirement`.
- **spec@1**: required `id, purpose, scope, non_goals[](min1), acceptance_criteria[](min1)`; each criterion: required `id, criterion`, optional `is_error_case(bool), judgment_call(bool), rationale(required if judgment_call true)`; optional `api_surface[]` (each: required `name,signature,description`, optional `error_conditions[]`), `linked_requirement, linked_research, spec_file_path, revision_note`. (canon-architect's variant adds ad-hoc `invariant_check` per criterion, not in the base schema.)
- **plan@1**: required `goal, architecture, tech_stack[], tasks[](min1)`; each task: required `id, title, files{create[],modify[],test[]}, steps[](min1), commit_message`, optional `depends_on[], covers_criteria[]`; optional `linked_spec, spec_file_path, spec_hash, linked_requirement`.
- **changeset@1**: required `summary(≤200 chars), files_changed[](min1), acceptance_criteria_met[](min1)`; optional `tests_added[], criteria_evidence[]` (each: required `criterion_id,test_file,implementation_file`, optional `test_line,implementation_line` — line numbers omitted rather than fabricated when reconstructed from a diff with no lambda run behind it), `breaking_changes[], commits[], linked_spec, linked_plan, linked_requirement`.
- **verdict@1**: required `verdict(enum pass/fail), confidence(enum high/medium/low), verdict_summary(≤300 chars)`; optional `blockers[]` (required on fail; each: required `criterion,finding`, optional `location`), `artifact_type, retry_count`.
- **finding-report@1**: required `workspace, language, findings[]`; each finding: required `id, description, file, line, severity(enum critical/high/medium/low), trigger_condition, root_cause, verdict(enum confirmed/plausible)`, optional `remediation_sketch`; optional `modules_scanned[], dead_files_excluded[]`.
- **release-artifact@1**: required `version, date(ISO8601), changesets[](min1)`; each changeset entry: required `summary, type(enum feat/fix/breaking/docs/chore)`, optional `linked_requirement, pr_url, commits[]`; optional `breaking_changes[], migration_guide`.
- **candidate@1** (proof-internal, scanner→adversary): required `id, file, line, taxonomy, excerpt`, optional `grep_pattern`.
- **field-survival-map@1** (proof-internal, boundary-tracer→adversary): required `candidate_id, struct_or_type, fields[], reasoning`; each field: required `name, reaches_boundary(bool|"uncertain"), boundary_type(enum network/subprocess/storage/render/none/unknown), evidence, last_observed_site`.
- **mutation-report@1** (lambda-internal, mutator→exit-gate/implementer): required `tool_used(enum cargo-mutants/stryker/tool_unavailable), mutants_tested, survived_mutants[], precision_tests[], verdict(enum pass/fail/tool_unavailable), reasoning`.

## End-to-end example

`docs/pipeline-walkthrough.md` traces one feature ("configurable HTTP timeout") through all 9 plugins with real JSON at every handoff, worth reading directly if you want the full worked example rather than my paraphrase — it's short (~300 lines) and demonstrates: (1) trace flagging a specific historical precedent (a `proxy_url` field silently dropped for 6 weeks) that becomes a targeted spec criterion (`ac-1`) requiring the field to *reach the builder call site*, not just exist in the struct; (2) `lambda-mutator` catching a slot-swap bug (implementer wired `read_timeout_ms` into the connection-timeout slot) that the unit test's own assertion couldn't distinguish, and generating a precision test that becomes permanent; (3) `proof` finding a real T7 (write-only field) bug independently — `private_registry` captured into config but never reaching the publish subprocess — and `canon-architect` refusing to patch the instance, instead widening the `publish()` parameter type to accept the full config struct with a `#[deny(unused_variables)]` compile-time invariant so the *next* dropped field is a compiler error, not a silent bug.
