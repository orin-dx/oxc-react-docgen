# Rolldown PluginDriver Architecture — Deep Research Report

## 1. Source File Map

The PluginDriver implementation is split across the `rolldown_plugin` and `rolldown_binding` crates:

| File | Role |
|------|------|
| `crates/rolldown_plugin/src/plugin_driver/mod.rs` | Core struct definition, tokio channels, module-loader integration |
| `crates/rolldown_plugin/src/plugin_driver/build_hooks.rs` | Build-phase hook dispatch (resolveId, load, transform, buildStart, etc.) |
| `crates/rolldown_plugin/src/plugin_driver/output_hooks.rs` | Output-phase hook dispatch (renderChunk, generateBundle, writeBundle) |
| `crates/rolldown_plugin/src/plugin_driver/plugin_driver_factory.rs` | Pre-sorts plugins by `order: pre/post` at initialization |
| `crates/rolldown_binding/src/options/plugin/js_plugin.rs` | NAPI bridge: wraps JS callbacks as Rust `Plugin` trait impls |
| `crates/rolldown_binding/src/options/plugin/parallel_js_plugin.rs` | Manages pools of JS plugin instances across workers |
| `crates/rolldown_binding/src/worker_manager.rs` | Semaphore-based worker-slot pool |
| `packages/rolldown/src/plugin/bindingify-build-hooks.ts` | JS side: wraps user hook functions into NAPI-compatible async closures |

## 2. PluginDriver Struct

`PluginDriver` (in `mod.rs`) holds:

- `plugins: IndexPluginable` — plugin instances
- `contexts: IndexPluginContext` — per-plugin context objects
- `module_infos: SharedModuleInfoDashMap` — module metadata (shared across threads via `DashMap`)
- `transform_dependencies: Arc&lt;DashMap&lt;ModuleIdx, Arc&lt;FxDashSet&lt;ArcStr&gt;&gt;&gt;&gt;` — HMR dependency tracking
- `file_emitter: SharedFileEmitter`

- **`tx: Arc&lt;Mutex&lt;Option&lt;tokio::sync::mpsc::UnboundedSender&lt;ModuleLoaderMsg&gt;&gt;&gt;&gt;`** — module loader integration via tokio mpsc

The presence of `tokio::sync::mpsc` and `tokio::sync::broadcast` in the struct confirms tokio is the async runtime.

## 3. Async Runtime: Tokio

Rolldown initializes a **custom tokio runtime** (not the default). Configuration is via environment variables:

- `ROLLDOWN_MAX_BLOCKING_THREADS` — number of threads for blocking operations (default: 4)
- `ROLLDOWN_WORKER_THREADS` — number of tokio worker threads (default: 1.5× CPU count)

**All bundling work, including plugin hook dispatch, runs on tokio worker threads.** This is confirmed by real-world crash reports that show stack traces labeled `thread 'tokio-runtime-worker'` while executing plugin-related code ([Issue #192](https://github.com/vitejs/rolldown-vite/issues/192), [Issue #196](https://github.com/vitejs/rolldown-vite/issues/196), [Issue #6561](https://github.com/rolldown/rolldown/issues/6561)).

The NAPI-RS `#[napi]` and `#[napi(async)]` macros on `rolldown_binding` functions bridge between Node.js and the tokio runtime.

---

## 4. Hook Dispatch Patterns

`build_hooks.rs` implements three dispatch strategies:

### First-Wins (short-circuit)
Used by: `resolveId`, `load`, `resolveDynamicImport`, `transformAst`

```rust
for plugin in self.iter_plugin_with_context_by_order() {
    let ret = plugin.call_resolve_id(...).await?;
    if ret.is_some() { return Ok(ret); }
}
```

### Sequential All-Plugins
Used by: `buildStart`, `buildEnd`, `moduleParsed`, `transform`, `generateBundle`

Iterates all plugins in order; each plugin receives the prior plugin's output as input. Each awaits before the next runs — no concurrency within a single hook type.

### Parallel (via ParallelJsPlugin)
Used by: `buildStart`, `buildEnd`, `moduleParsed`, `writeBundle` when using the parallel plugin wrapper.

`ParallelJsPlugin` calls `run_all()`, which uses `future::join_all` to fire all worker plugin instances concurrently.

**Hook ordering** is configured via `PluginHookMeta { order: pre | post | None }`, pre-sorted by `PluginDriverFactory` at initialization.

## 5. JS Plugin Execution: Which Thread?

This is the nuanced part. There are two layers:

**Layer 1 — Rust dispatch (tokio worker threads):** `PluginDriver::build_hooks.rs` calls `plugin.call_resolve_id()` etc. on tokio worker threads.

**Layer 2 — JS callback re-entry (Node.js event loop):** `JsPlugin` (in `js_plugin.rs`) implements the `Plugin` trait using NAPI-RS's `await_call()`, which marshals JS promise execution back to the Node.js event loop thread. The JS hook handler runs on the Node.js main thread / event loop, not on a tokio worker thread. NAPI-RS handles this boundary crossing.

So the flow is:
```
tokio worker thread
  → PluginDriver iterates plugins
  → JsPlugin::call_hook() via await_call()
  → [NAPI boundary crossing]
  → Node.js event loop thread
    → JS async function executes (user's plugin code)
    → promise resolves
  → [NAPI boundary crossing back]
  → tokio worker thread resumes with result
```

**For `ParallelJsPlugin`:** Multiple `JsPlugin` instances are managed by `WorkerManager`, which maintains a semaphore pool of integer indices. `run_single()` acquires one worker slot; `run_all()` acquires all slots and uses `future::join_all`. The actual worker instances correspond to Node.js worker threads (separate event loops), allowing true parallelism for JS plugins — this is why it's called "parallel JS plugin."

## 6. NAPI Bridge Details

**JS side** (`bindingify-build-hooks.ts`): User hook functions are wrapped as `async (ctx, ...args) =&gt; { return await handler.call(pluginCtx, ...) }`. Results are serialized into NAPI-compatible Rust structs.

**Rust side** (`js_plugin.rs`): Each hook method uses `cb.await_call(args.into()).instrument(debug_span!("hook_name")).await?`. The `await_call` pattern is NAPI-RS's mechanism for calling JS async functions from Rust and awaiting their promises.

**Filter optimization:** Before crossing the NAPI boundary, Rolldown evaluates filter expressions in Rust. `filter_expr_cache` caches compiled filter expressions. Hooks (`transform`, `load`, `resolveId`, `renderChunk`) only invoke the JS callback if the filter matches — this significantly reduces unnecessary JS boundary crossings.

## 7. Deadlock Risk (Issue #7311)

A known architectural hazard documented in [Issue #7311](https://github.com/rolldown/rolldown/issues/7311): if a **sync** NAPI function acquires a lock (e.g., a `DashMap` entry) and a JS hook called from within that context tries to call back into Rust via another sync NAPI function that needs the same lock, a deadlock occurs. This happened with `register_modules` in the dev engine.

Identified at-risk functions:
- HIGH: `remove_client` in `binding_dev_engine.rs`
- MEDIUM: `register_plugins` in `parallel_js_plugin_registry.rs`, `emit_file`/`emit_chunk` in `binding_plugin_context.rs`

Mitigation: convert sync NAPI functions to `async` (using `#[napi] pub async fn`) so lock acquisition can yield the thread.
