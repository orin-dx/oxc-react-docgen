# Edge Cases & Failure Modes

A comprehensive audit of non-happy-path behavior across the pipeline: extractor, resolver, pipeline/cache/import_map, CLI/config/NAPI binding, and types/serialization/plugin. Produced by five parallel read-only audits against the codebase as of 2026-08-04, cross-checked against existing test coverage.

**Status update (2026-08-12):** the 43-task remediation plan derived from this audit (see `root-cause-analysis.md` and `docs/superpowers/plans/2026-08-04-edge-case-remediation.md`) has landed on `main`. Every P0 and P1 finding below is fixed except P0-2 (cache staleness — deliberately deferred, now documented in a code comment rather than fixed, see its entry). Most P2/P3 findings are also fixed; a handful of extractor detection-pattern gaps were explicitly scoped out as separate feature work (new component-shape recognition, not diagnostic-discipline fixes) and remain open — marked individually below. This doc is kept as the historical record of what was found; strikethrough + **FIXED** marks resolved items rather than deleting them, so the audit trail stays intact.

**How to read this doc:** findings are grouped by severity tier first (for prioritization), then by subsystem (for context when doing the actual fix). "Tested?" means an existing test exercises exactly this behavior, not just the surrounding happy path.

---

## Severity tiers

- **Crash/hang** — can panic, OOM, or hang the process on realistic or adversarial input.
- **Silent data loss** — violates CLAUDE.md non-negotiable #6 ("always emit a Diagnostic when degrading — never fail silently"): output is missing or incomplete with no trace.
- **Silent correctness bug** — output is present but *wrong*, not just missing, with no trace.
- **Contract inconsistency** — behavior diverges from a documented or implied contract (exit codes, schema, precedence rules already established elsewhere in the same codebase).
- **Documented/by-design limitation** — already tracked in `rdt-coverage.md` or `type-checker-integration.md`; listed here only for completeness.

## Documented/by-design limitations (listed for completeness, not new findings)

- Ariakit's `Props<T, O> = O & Omit<ComponentPropsWithoutRef<T>, keyof O>` generic pattern is unmatched at the chain level — `composes` stays empty for 6 of the 10 outlier components tracked in `docs/benchmarks.md`. Matches the already-documented gap.
- Mapped types, conditional types, and a couple of `@emotion/styled`-specific call shapes need real type inference OXC deliberately doesn't do — tracked in `docs/type-checker-integration.md` and `rdt-coverage.md`'s known-gaps table.
- Multi-root/monorepo ambient-global (`lib.dom.d.ts` etc.) resolution only inspects `options.src_dirs.first()` — if the first `src_dir` can't resolve `typescript` but a later one could, ambient lookups silently return empty for the whole run. Currently treated as legitimate silent degradation by design; flagged here only because it's untested against an actual multi-root config.
- TOON's format is deliberately lossy relative to canonical JSON (truncated unions, no length cap on descriptions) but this isn't stated in the module's own doc comment — a documentation gap, not a behavior bug.

## Notable non-findings (checked, confirmed sound)

- No `unwrap()`/`expect()`/`panic!()` outside `#[cfg(test)]` anywhere in the extractor, resolver, CLI, or binding crates — non-negotiable #1 holds everywhere it was checked.
- Import re-export cycles are correctly bounded (`MAX_REEXPORT_DEPTH = 8` plus a visited set) with dedicated tests.
- Parallel parse/merge is deterministic: discovery sorts, rayon preserves input order through `collect()`, and the sequential merge phase iterates that same order — diagnostics ordering and dedup winner-selection are reproducible.
- Editor atomic-save patterns (temp file + rename) are explicitly handled in watch mode via `canonicalize_best_effort`.
- Shell injection in config loading is not possible — the config path is passed via `env()`, never interpolated into a shell string, verified across all code paths.

## Watch mode — new, previously-untracked bug (found and fixed 2026-08-12 via Phase 3 spec-drift validation against SPEC-PIPELINE-001)

- **FIXED.** `WatchSession::update_file` bound `new_global` directly to `ArcSwap::rcu(...)`'s return value — but `rcu` returns the value from *before* the swap (arc-swap's `compare_and_swap` convention: the returned `prev` is the pre-update value), not the value the closure just produced. Every incremental watch update therefore re-resolved affected components against the file's content from *before* the edit that triggered the update — watch mode was permanently one edit behind. Confirmed against `arc-swap` 1.9.1's own source (`rcu`'s `compare_and_swap`/`prev` naming) before fixing. This was caught by `canon-drift-checker`'s validation of `SPEC-PIPELINE-001`'s AC-015/AC-020/AC-024 against live source and a probe — the spec was correct, the code was wrong, and no existing test caught it (the whole watch-mode test suite only asserted component *identity*, which is invariant under this bug — a component named `Widget` stays named `Widget` regardless of which version of its props resolved). **FIXED**: `rcu`'s return value is now discarded and `new_global` is re-read via `self.global.load_full()` after the swap completes. Test: `update_file_reflects_the_edited_files_new_content_not_its_pre_edit_content` (asserts prop *content* changes across an edit, not just component presence) — verified to fail cleanly against the pre-fix code before being confirmed against the fix. | `pipeline/watch.rs:171` |

- **FIXED.** A relative `--config` path whose parent directory differs from the process's actual cwd failed with `ERR_MODULE_NOT_FOUND` even though the file existed (e.g. `--config plain/docgen.config.ts` from the repo root). Root cause: `try_load_config` changes the spawned node subprocess's cwd to the config file's parent (so `tsx`/imports resolve relative to the config, not to wherever the CLI was invoked from), but passed the original *relative* path string through unchanged in `__DOCGEN_CONFIG_PATH` — node then re-resolved that same relative string against the *new* cwd it had just been given. **FIXED**: the path is now canonicalized before being passed to the subprocess, falling back to the original (relative) path if canonicalization fails so a genuine "file not found" error still names what the user typed. **Watch mode — component_cache staleness, strengthened (2026-08-12):** Phase 3 validation independently reconfirmed the `component_cache` bare-name-vs-disambiguated-key mismatch already tracked above, and found a second manifestation of the same underlying design gap: `update_file` never *evicts* a stale entry when a component is renamed between edits (`Card` renamed to `Panel` leaves both `"Card"` and `"Panel"` present in `component_cache`, since the incremental path only ever inserts under the new key and nothing removes the old one). Both manifestations trace to the same root cause — `component_cache.insert(entry.display_name.clone(), ...)` is a pure insert with no corresponding eviction of whatever key(s) that file's components previously occupied. **Still open** — the fix likely needs `update_file` to track and remove a file's previous component keys before inserting its newly-resolved ones, not just a disambiguation-rule fix.

## LSP — new bug found and fixed 2026-08-12 via Phase 3+ spec-drift validation

- **FIXED.** Under `-v`/`-vv` (verbose tracing), `tracing::error!` calls inside `lsp.rs` were written to **stdout** by the default `tracing_subscriber::fmt` writer — corrupting the LSP transport channel, which requires stdout to carry only well-formed `Content-Length`-framed messages. A real editor session with verbose logging enabled would see this ANSI-colored diagnostic text injected mid-stream, desyncing the client. **FIXED**: `init_tracing` now routes all tracing output through `.with_writer(std::io::stderr)` — global, not LSP-specific, since stderr is safe for every command. Tests: `crates/cli/tests/lsp_process.rs`'s `verbose_mode_never_writes_tracing_output_to_stdout` (confirmed to fail against the pre-fix code, capturing the exact leaked ANSI-colored error line), plus 3 new process-level tests (`oversized_content_length_exits_1_with_empty_stdout`, `headerless_frame_exits_1_with_empty_stdout`, `well_formed_initialize_gets_a_response_frame_with_hover_false`) driving the real binary's stdin/stdout instead of only its pure helper functions. | `cli/main.rs:205-216` |
