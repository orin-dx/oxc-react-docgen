### 1. Component detection edge cases

Covered by existing tests: FC annotation (`test_fc_pattern`), forwardRef (`test_display_name_update`), memo(forwardRef) (`test_memo_forward_ref_detected`), HOC-wrapped (`test_hoc_pattern`), bare function decl (Pattern 4), forwardRef+as-cast (`test_forward_ref_component_annotation_with_as_cast`, `test_forward_ref_explicit_generics_survives_as_cast`), bare-identifier alias/rename (`test_bare_identifier_passthrough_alias_renames_component`, `test_identifier_wrapped_component_renamed_to_export_binding`), two aliases to one base (`test_two_aliases_to_the_same_base_component_both_survive`), `.d.ts` ForwardRefExoticComponent (component.rs:230, exercised via `test_radix_button_dts` but that test only checks interface collection, not component_mappings).

Gaps (silent misses, no diagnostic):
- **Anonymous default export** (`export default function(props: Props) {}`) — `visit_function` (visit.rs:262-293) requires `func.id` to be `Some` (line 265). Anonymous default-exported function components are silently skipped. No test covers this; likely a real-world miss (common in Next.js-style page files). Severity: silent data loss.
- **Class components** — no handling anywhere in `visit.rs`/`component.rs` for `Declaration::ClassDeclaration` as a component (only `declaration_name`, mod.rs:755, picks up the name for exports). `class Button extends React.Component<Props>` never produces a `ComponentMapping`. Undocumented gap.
- **`Object.assign(Component, { Sub: ... })` compound-component pattern** — not handled; `static_member_assignment` (interface.rs:193-201) only matches `X.Y = ...`, not `Object.assign` calls.
- **Generic components** (`function Comp<T>(props: Props<T>)`) — `func.type_parameters` is never recorded (unlike interfaces/type aliases, which do save them at visit.rs:145-150, 167-172), so a bare `T` referenced inside `Props<T>`'s body isn't recognized as a component-level generic placeholder. Asymmetry, not crash risk.
- **class expression as component** (`const Button = class extends React.Component<Props> {}`) — not handled by any `try_*` in component.rs; silently falls through all detectors.
- `export { X as Y }` renaming — `LexedExport` records local/exported name distinction correctly (visit.rs:61-96) but is a separate table from `component_mappings`; reconciliation is resolver territory (out of scope), flagged as a seam.

### 2. Prop-type declaration parsing edge cases

Covered: Omit/Pick/Partial/Required/Readonly (alias.rs), unions incl. literal unions, intersections, inline object literal type-alias bodies, bare function-type aliases, bare array/tuple aliases (mod.rs:805-902, explicitly regression-tested against a documented prior silent-vanishing bug), namespaced types via `namespace_stack`/`ts_type_name_str` (`test_namespace_member_stored_under_qualified_name`), `readonly T[]` type operator (`test_readonly_array_type_operator_peeled_transparently`).

Gaps:

### 3. JSDoc parsing edge cases

Covered: proximity-based JSDoc→interface-description-not-first-prop (`test_interface_description_not_stolen_by_first_prop`), `@deprecated` non-bleed to untagged siblings (`test_deprecated_tag_does_not_bleed_to_sibling_props_without_jsdoc`).

Gaps:
- `PROXIMITY_THRESHOLD = 120` bytes (jsdoc.rs:33) is an untested heuristic boundary — a prop preceded by a long decorator chain or several blank lines beyond 120 bytes silently gets no JSDoc, no diagnostic.
- **Non-JSDoc block comments leak as descriptions**: `find_jsdoc_with_tags` only checks `c.is_block` (jsdoc.rs:44), not that the comment starts with `/**` specifically — plain `/* comment */` blocks also satisfy `is_block()`. `parse_jsdoc_text`'s `trim_start_matches("/**")` (jsdoc.rs:66) is a no-op on such input, so a stray non-JSDoc block comment within 120 bytes of a prop can leak into its description. No test verifies single-star blocks are excluded. Severity: cosmetic/silent data quality, no diagnostic.
- JSDoc placed above a re-export statement (`/** ... */\nexport { X } from './y'`) is never associated with anything — `visit_export_named_declaration` (visit.rs:61-96) never calls `find_jsdoc`. Silent, untested.

### 4. Default value extraction edge cases

Covered: destructured defaults (`extract_param_defaults`, defaults.rs), `defaultProps` static assignment merge incl. displayName-rename interaction (`test_default_props_assignment_merged_into_component_mapping`, `test_default_props_scan_survives_a_displayname_rename_to_a_different_string`), computed vs. literal defaults distinguished via `computed` flag (defaults.rs:47-78).

Gaps:

### 5. Panic/crash risks

No bare `.unwrap()`/`.expect()`/`panic!()` outside `#[cfg(test)]` found in component.rs, alias.rs, interface.rs, jsdoc.rs, defaults.rs, or visit.rs — consistent with the project's non-negotiable. All fallible paths use `?`/`let-else`/`Option` combinators.

- **Slicing risk (currently sound, but fragile invariant)**: every raw-text fallback (`self.source[span.start as usize..span.end as usize]` — mod.rs:332,335,459,467,493,511; defaults.rs:63,73; jsdoc.rs:53) trusts OXC span byte-offsets to be in-bounds and on UTF-8 char boundaries for `self.source`. Sound today because `self.source` is exactly what OXC parsed (`parse_file`, mod.rs:104-124), but zero defensive checks exist; no inline test stresses multi-byte UTF-8 near a span boundary (emoji/CJK in JSDoc or string literals).
- **Real crash-risk gap — recursion depth in `ts_type_to_collected`** (mod.rs:311-471): recurses per nested `CollectedType` (Union/Intersection/Array/Tuple/Function/Conditional/Mapped) with no independent depth counter of its own; relies entirely on the pre-parse `max_bracket_nesting_depth` heuristic (mod.rs:40, guard at 105-120) to bound worst-case recursion. That heuristic counts *brackets*, not *type nesting* specifically — deeply chained conditional types (`A extends B ? C extends D ? ... : ... : ...`) can achieve deep type-nesting with proportionally fewer brackets per level than object-literal/paren nesting. The guard's own docstring (mod.rs:38-40) claims to cover "nested parenthesized types, object type literals, or conditional types," but the only test (`test_excessive_nesting_guard`) uses pure `(...)` paren nesting, which maps 1:1 to bracket count and doesn't validate the conditional-type case. This is an untested stack-overflow risk under adversarial/pathological conditional-type-heavy input.
