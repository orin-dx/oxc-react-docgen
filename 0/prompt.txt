## 3. The semantic model — this is the "system model" you're looking for

`.claude/semantic-model/INDEX.md` is a ~400-token router, explicit about NOT loading everything:

> "Read this first. Load only the files your task requires — never load all files at once. The goal is progressive loading: ~400 tokens here, then ~1500 tokens per topic file loaded."

It has a task->file lookup table (e.g. "apply.rs, version writing, idempotency" -> load `version-flow.md`, `error-taxonomy.md`) and explicitly states the hierarchy:

> "Do NOT load semantic-model files when implementing a track unless the spec explicitly references them. The spec@1 is the authority; these files are the reference layer beneath it."
> "What Does NOT Live Here — Source code (read directly from the crate). Spec@1 artifacts (`.claude/specs/`). Active task tracking (`.claude/plans/ACTIVE.md`). Prose design docs (`docs/` — treat as human reference, not invariant source)."

So the layering is: **source code** (ground truth) -> **semantic-model/*.md** (curated invariants extracted from source, small, targeted) -> **spec@1** (testable criteria for one unit of work, may cite semantic-model decisions) -> **plan@1** (task breakdown) -> **docs/*.md** (long-form human prose, explicitly demoted to "not invariant source").

Each semantic-model file states its `Source:` (the actual .rs file(s) it's distilled from) at the top, e.g. `core-identity.md` opens with `Source: crates/callisto-model/src/identity.rs`. Content is a mix of type definitions (verbatim Rust), enumerated invariants (numbered, e.g. the six `matches()` invariants in core-identity.md — "These invariants are intentional and must not be changed"), and locked design decisions with a name ("Track E Design Decision (Option 3)") plus a pointer forward to the spec that operationalizes it: *"See `.claude/specs/track-e-specificity.json` for the full testable acceptance criteria."*

`error-taxonomy.md` is essentially a hand-maintained table of every error variant with its E-code, is genuinely a domain glossary (GraphError vs ConfigError, transparent vs non-transparent variants), and even documents known gaps candidly: three ConfigError variants are marked "Defined but NEVER EMITTED — known gap."

This is the artifact that most directly answers your question #3 — it's not a diagram or ERD, it's markdown files scoped one-per-subsystem, each anchored to real source, cross-linked to the specs that depend on them, with an index file that prevents full-context loading. It functions like a distilled, LLM-context-budget-aware domain model rather than a single monolithic architecture doc.
