# NAPI-RS v3 Binary Package Publishing — Canonical Reference

Sources: `oxc-transform@0.136.0` (fetched live from unpkg), `@swc/core@1.15.41` (unpkg), `@napi-rs/package-template-linux-x64-gnu` (unpkg), `napi-rs/package-template` and `napi-rs/package-template-pnpm` (GitHub), napi.rs CLI docs, Rspack/OXC/Rolldown source repositories.

## 1. Canonical Directory Structure

```
packages/napi/
├── package.json          # committed; NO optionalDependencies (injected at publish time)
├── index.js              # auto-generated by `napi build`; commit it
├── index.d.ts            # TypeScript types (you already have this)
├── browser.js            # optional: WASM/browser fallback
└── npm/                  # platform subpackages — each published as a separate npm package
    ├── darwin-arm64/
    │   ├── package.json  # { "os": ["darwin"], "cpu": ["arm64"], "main": "napi.darwin-arm64.node" }
    │   └── napi.darwin-arm64.node    # NOT committed; placed here by `napi artifacts` in CI
    ├── darwin-x64/
    ├── linux-x64-gnu/
    ├── linux-x64-musl/
    ├── linux-arm64-gnu/
    ├── linux-arm64-musl/
    ├── win32-x64-msvc/
    └── ...
```

The `.node` binaries are **never committed to git**. They are built per-platform in CI and placed into `npm/&lt;platform&gt;/` by `napi artifacts`. Run `napi create-npm-dirs` once to scaffold all the `npm/&lt;platform&gt;/package.json` files.

## 2. Main `package.json` — What You Commit vs What Gets Published

**Critical finding:** `optionalDependencies` is **absent from the committed `package.json`**. It is injected entirely by `napi prepublish -t npm` at publish time. Both the napi-rs template and `oxc-transform` confirm this — no `optionalDependencies` in source.

## 3. Platform-Specific Package Naming and Structure

**Naming convention:** `@&lt;scope&gt;/&lt;name&gt;-&lt;os&gt;-&lt;cpu&gt;[-&lt;libc&gt;]`

Real examples:
- OXC: `@oxc-transform/binding-linux-x64-gnu`, `@oxc-transform/binding-darwin-arm64`
- SWC: `@swc/core-linux-x64-gnu`, `@swc/core-darwin-arm64`
- Template: `@napi-rs/package-template-linux-x64-gnu`

The `&lt;libc&gt;` suffix (`-gnu` vs `-musl`) only appears for Linux. macOS and Windows have no libc qualifier.

**`npm/linux-x64-gnu/package.json`** (from `@napi-rs/package-template-linux-x64-gnu` on unpkg, verbatim):

```json
{
  "name": "@oxc-react-docgen/napi-linux-x64-gnu",
  "version": "0.1.0",
  "os":  ["linux"],
  "cpu": ["x64"],
  "main": "napi.linux-x64-gnu.node",
  "files": ["napi.linux-x64-gnu.node"],
  "engines": { "node": "&gt;= 18" },
  "publishConfig": { "registry": "https://registry.npmjs.org/", "access": "public" }
}
```

Newer packages (oxc-transform) also add `"libc": ["glibc"]` for the GNU packages — npm and pnpm use `os`/`cpu`/`libc` to skip installation on non-matching platforms.

**Binary filename:** `&lt;binaryName&gt;.&lt;os&gt;-&lt;cpu&gt;[-&lt;libc&gt;].node` — e.g. `napi.linux-x64-gnu.node`.

## 4. The `index.js` Shim

NAPI-RS auto-generates this via `napi build`. Commit the generated file; it is overwritten on each rebuild. The actual `oxc-transform@0.136.0/index.js` (fetched live, ESM variant since it has `"type": "module"`):

```js
/* auto-generated by NAPI-RS */
import { createRequire } from 'module'
const require = createRequire(import.meta.url)
const __dirname = new URL('.', import.meta.url).pathname
const { readFileSync } = require('fs')

let nativeBinding = null
const loadErrors = []

// --- musl detection (3 strategies) ---
const isMusl = () =&gt; {
  // 1. readFileSync('/usr/bin/ldd').includes('musl')
  // 2. process.report.getReport() — checks glibcVersionRuntime + sharedObjects
  // 3. execSync('ldd --version').includes('musl')
}

function requireNative() {
  // Escape hatch
  if (process.env.NAPI_RS_NATIVE_LIBRARY_PATH) {
    try { return require(process.env.NAPI_RS_NATIVE_LIBRARY_PATH) } catch (e) { loadErrors.push(e) }
  }
  if (process.platform === 'darwin') {
    // 1. Try local .node (monorepo dev): require('./napi.darwin-arm64.node')
    // 2. Try optional dep (consumer install): require('@oxc-react-docgen/napi-darwin-arm64')
    //    + optional version mismatch check via NAPI_RS_ENFORCE_VERSION_CHECK env
  } else if (process.platform === 'linux') {
    if (isMusl()) {
      // ./napi.linux-x64-musl.node → @oxc-react-docgen/napi-linux-x64-musl
    } else {
      // ./napi.linux-x64-gnu.node  → @oxc-react-docgen/napi-linux-x64-gnu
    }
  } else if (process.platform === 'win32') {
    // win32-x64-msvc, win32-arm64-msvc, win32-ia32-msvc
  }
  // ... android, freebsd, openharmony ...
}

nativeBinding = requireNative()

// WASI fallback (NAPI_RS_FORCE_WASI='true'|'error')
if (!nativeBinding || process.env.NAPI_RS_FORCE_WASI === 'true') {
  try { nativeBinding = require('./napi.wasi.cjs') } catch (e) { loadErrors.push(e) }
  try { nativeBinding = require('@oxc-react-docgen/napi-wasm32-wasi') } catch (e) { loadErrors.push(e) }
}

if (!nativeBinding) {
  throw new Error(
    `Cannot find native binding. npm has a bug related to optional dependencies ` +
    `(https://github.com/npm/cli/issues/4828). ` +
    `Please try \`npm i\` again after removing both package-lock.json and node_modules.`,
    { cause: loadErrors.reduce((err, cur) =&gt; { cur.cause = err; return cur }) }
  )
}

// Named exports match your #[napi] annotated functions:
const { extractAll, createSession, initializeSession, extractFileIncremental, closeSession } = nativeBinding
export { extractAll, createSession, initializeSession, extractFileIncremental, closeSession }
```

**Load order per platform entry:**
1. `NAPI_RS_NATIVE_LIBRARY_PATH` env override
2. Local `.node` file: `require('./napi.darwin-arm64.node')` — works in monorepo after `cargo build`
3. Optional npm package: `require('@oxc-react-docgen/napi-darwin-arm64')` — works for npm consumers
4. WASI `.wasi.cjs` local, then `@…/napi-wasm32-wasi` package
5. Throw with npm bug hint

If your package has `"type": "module"`, you get ESM output (above). Without it, CJS output (`module.exports = nativeBinding`). OXC uses ESM; the napi-rs template uses CJS.

## 5. `napi build` vs `napi artifacts` vs `napi prepublish`

| Command | Run where | Does what |
|---|---|---|
| `napi build --platform --release` | Per-platform CI runner | Runs `cargo build`, writes `napi.&lt;platform&gt;.node` + regenerates `index.js` + `index.d.ts` |
| `napi artifacts` | Publish job | Reads `./artifacts/&lt;platform&gt;.node` files (downloaded from CI), copies them into `npm/&lt;platform&gt;/napi.&lt;platform&gt;.node` |
| `napi prepublish -t npm` | `prepublishOnly` hook | Injects `optionalDependencies` into `package.json`, publishes each `npm/&lt;platform&gt;/` as a separate npm package, creates GitHub Release |
| `napi version` | Version bump | Propagates version change to all `npm/&lt;platform&gt;/package.json` files |
| `napi create-npm-dirs` | One-time setup | Scaffolds `npm/&lt;platform&gt;/package.json` stubs for all targets in `napi.targets` |

**CI flow:**
```
[git tag push]
  ├─ build matrix (parallel, one runner per platform):
  │    napi build --platform --release --target &lt;triple&gt;
  │    upload-artifact: napi.&lt;platform&gt;.node
  │
  └─ publish job (ubuntu-latest):
       download-artifact --pattern bindings-*  →  ./artifacts/
       napi artifacts                          →  npm/&lt;platform&gt;/napi.&lt;platform&gt;.node
       napi prepublish -t npm                 →  publishes all platform pkgs + root pkg
```

Cross-compilation on Linux:
- `--use-napi-cross` flag for `aarch64-unknown-linux-gnu`, `armv7-unknown-linux-gnueabihf` (uses `@napi-rs/cross-toolchain`)
- `-x` (zigbuild) for musl targets

## 6. pnpm Workspace: `"@oxc-react-docgen/napi": "workspace:*"`

**Yes, this works.** It is the standard pattern used by Rolldown and OXC.

```json
// packages/vite-plugin/package.json
{
  "dependencies": {
    "@oxc-react-docgen/napi": "workspace:*"
  }
}
```

pnpm resolves this to a symlink into `packages/napi/`. When `index.js` runs, the load order works correctly in the monorepo:

- **Step 2 (local `.node`):** `require('./napi.darwin-arm64.node')` resolves relative to `packages/napi/`. If you ran `napi build --platform` (or `cargo build` + manual copy), the binary is there.
- **Step 3 (optional dep):** falls back to `require('@oxc-react-docgen/napi-darwin-arm64')` — won't be in workspace `node_modules` unless you add `optionalDependencies: { "@oxc-react-docgen/napi-darwin-arm64": "workspace:*" }` to the napi package (the Rspack approach) or publish first.

**For local dev in the monorepo, the simplest approach:** run `napi build --platform` (or `CARGO_TARGET_DIR=… cargo build -p oxc-react-docgen-napi`) to put the `.node` file in `packages/napi/`. The workspace symlink from `vite-plugin` to `packages/napi/` means the shim finds it immediately.

`NAPI_RS_NATIVE_LIBRARY_PATH` env var provides an explicit escape hatch if you need to point at a non-standard path.

**pnpm correctly handles optionalDependencies** using `os`/`cpu`/`libc` fields — only the matching platform package is installed. No special configuration needed.

When you publish, pnpm converts `workspace:*` → the resolved semver version automatically in the published tarball.

## 7. Consumer's `package.json`

**Consumers install nothing extra.** They just add your vite plugin:

```json
{
  "devDependencies": {
    "@oxc-react-docgen/vite-plugin": "^0.1.0"
  }
}
```

The chain: `@oxc-react-docgen/vite-plugin` has `dependencies: { "@oxc-react-docgen/napi": "^0.1.0" }` (regular dep, not peer). The published `@oxc-react-docgen/napi` has `optionalDependencies` listing all platform binaries with exact-pinned versions. npm/pnpm/yarn install only the one matching the consumer's platform.

The consumer never sees or thinks about the native binary. This is confirmed by `oxc-transform`, `@swc/core`, and `rolldown` — all use this identical pattern.

Your `packages/vite-plugin/package.json` should declare napi as a regular `dependency` (not peer, not optional):

```json
{
  "name": "@oxc-react-docgen/vite-plugin",
  "dependencies": {
    "@oxc-react-docgen/napi": "workspace:*"
  },
  "peerDependencies": {
    "vite": "^5.0.0 || ^6.0.0"
  }
}
```
