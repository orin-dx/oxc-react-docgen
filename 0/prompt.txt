=== 4. Cache subsystem (cache.rs) ===

- Corrupted/partial msgpack: try_load (:93-115) — `rmp_serde::from_slice(&bytes).ok()?` degrades to empty on any decode failure. Same shape as the tested schema-mismatch path (test_schema_version_mismatch_returns_empty); no direct corrupt-bytes test exists but the code path is provably identical/safe.
- Concurrent processes sharing a cache dir: no locking anywhere. Each process loads an independent in-memory DashMap at start; save_to_disk (:145-177) unconditionally overwrites via temp+rename. Last writer wins, silently dropping the other process's warmed entries. Not corruption (atomic rename prevents partial reads), purely lost cache-effectiveness. No test, low severity.
- mtime granularity — real, uncovered correctness gap. key_for (:181-191) keys on (path, size, mtime_ns). On filesystems/environments with coarser mtime resolution (1s on some setups, network FS, container overlay FS), an edit completing within the same mtime tick AND producing identical byte length is indistinguishable from the original — cache returns stale SourceData despite changed content. test_stale_key_after_content_change (:288-301) only tests a size-changing edit, sidestepping this case entirely. Scope is narrow (only .d.ts files are cached, per mod.rs:262's is_dts gate) but real — e.g. a build step rewriting a vendored .d.ts with same-length content within the same second.
- Eviction is not LRU — insert (:128-139) evicts 100 arbitrary entries via `self.store.iter().take(100)` (DashMap iteration order, unrelated to recency/frequency) once len() >= MAX_CACHE_ENTRIES. test_eviction_when_exceeding_max_entries only asserts the cap holds, not eviction policy. In large monorepos (multiple heavy @types packages, easily >5000 d.ts files) this could evict hot entries while cold ones survive — perf-only, no correctness risk.
- Nested TOCTOU inside the cache hit/miss path: a miss triggers key_for (stat #1 inside get, mod.rs:264), then content read (mod.rs:269), then a second independent key_for stat inside insert (cache.rs:129). If the file is edited between the content read and the insert's stat, the cache stores stale content under a newer key — a later read at that newer mtime/size gets served stale data. Narrow window, low severity, effectively untestable without fault injection.
- Read-only cache dir / bad path: try_save's create_dir_all(...).ok()? (:153) and the swallow-all-errors wrapper in save_to_disk (:145-150) are correct and directly covered by test_save_to_disk_never_panics_on_bad_dir.
