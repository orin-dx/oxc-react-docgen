## 3. Exit codes
Inconsistent across commands — only `extract` and `check` actually surface the error-diagnostic exit code:
- `extract` (main.rs:181): returns `cmd_extract`'s code (0 or 2). Correct, tested for both --json and non-json (extract.rs:180-196).
- `check` (main.rs:186): returns `cmd_check`'s code (0/1/2). Correct, tested for --json (check.rs:53-58).
- `watch` (main.rs:182-185): **always exits 0** — the initial extraction's diagnostics (including Error-severity ones) are printed but never affect the exit code, and `cmd_watch` returns `Result<()>` not `Result<i32>`. This may be intentional for a long-running dev-loop command, but it means `oxc-react-docgen watch` in a CI/pre-commit hook context (piped once, non-interactive) would report success even with hard extraction errors. **Worth confirming intent — flag as a gap if watch is ever used non-interactively.**
- `inspect` (main.rs:187-190): **always exits 0**, even if the named component isn't found — wait, actually `cmd_inspect` returns `Err` via `miette::miette!` when the component is missing (inspect.rs:20-26), which does propagate as a genuine process failure through `?` in main. So inspect only fails on missing-component, never on Error-severity diagnostics elsewhere in the tree (those are silently absent from cmd_inspect's output entirely — it doesn't call `print_diagnostics` at all). Lower severity since inspect is explicitly a "debugging tool."
- `schema` (main.rs:191-194) and `lsp` (main.rs:195-198): always 0 or process-terminate via `process::exit` (lsp only via its own `exit` method, or watch's 'q' key) — not diagnostic-dependent, not applicable.
- `completions` (main.rs:199-202): always 0, not applicable.

## 4. Output writing
- `--out` write failure: `std::fs::write` (extract.rs:61, watch.rs:110) is not atomic — it opens with truncate+create, writes, and on a mid-write failure (disk full, permission revoked mid-run) can leave a **truncated, corrupt partial file** at the target path rather than either the old content or nothing. No temp-file+rename pattern used anywhere in this crate. **Medium severity — affects both `extract --out` and `watch --out`, untested.**
- `watch --out`: writes happen once per file-change event (watch.rs:107-112), each one a fresh full-truncate write of the whole snapshot; concurrent writes aren't a risk since it's single-threaded through the watchexec callback, but the same non-atomicity applies on every re-write, and errors are silently swallowed (`if let Ok(json) = ... { let _ = std::fs::write(...) }` — the `Result` of `fs::write` itself is discarded (`let _ =`), so **a write failure during watch mode is completely silent**, no error printed, no diagnostic. This directly contradicts CLAUDE.md non-negotiable #6 ("never fail silently") even though that rule is phrased around `Diagnostic` degradation rather than I/O — the practical effect for a user is the same: silent, invisible failure. **Medium-high severity, untested.**

## 5. watch.rs
- Startup with existing errors: printed via `print_summary`/`print_diagnostics` (watch.rs:48-51) but as noted in §3, has zero effect on exit code — watch just keeps running. Reasonable for a dev tool.
- Ctrl-C mid-extraction: the raw-mode key-reader thread (watch.rs:58-76) calls `std::process::exit(0)` directly on 'q'/'c' key press — note this is keyboard 'q'/'c' input via crossterm raw mode, not the SIGINT signal; actual Ctrl-C (SIGINT) is not intercepted at all, so its behavior is whatever the OS default does mid-write (terminal raw mode may be left enabled if the process is killed by signal rather than the 'q' key path, since `disable_raw_mode()` only runs on the 'q'/'c' branch or after the key-loop's `while` exits — a raw SIGINT kill would leave the terminal in raw mode for the user's shell). **Medium severity — terminal corruption UX bug on real Ctrl-C, untested (would need a signal-handling integration test).**
- Progress/terminal interleaving: the spinner is only used for the *initial* extraction (watch.rs:32-47); per-file updates during the watch loop print plain `println!` lines (watch.rs:103-105) with no spinner conflict — looks fine.

## 6. lsp.rs
This is explicitly a scaffold (doc comment: "LSP scaffold"), and it shows:
- **No real extraction ever happens.** `cmd_lsp` never calls `oxc_react_docgen_core::pipeline::extract` or touches `src_dirs`/config at all — it only implements `initialize`/`shutdown`/`exit`. So "requests for files outside src_dirs," "hover on positions with no component," and "race between ready and first request" are all **not yet applicable** — there's no hover implementation despite `hoverProvider: true` being advertised in the initialize response (lsp.rs:56), which is itself a bug: a client will send `textDocument/hover` requests based on that capability and get silently ignored (the `_ => {}` catch-all, lsp.rs:78, sends no response for any unhandled method, including hover). **A JSON-RPC request without a response will hang the client indefinitely waiting for a reply** — this is worse than an error response. **High severity relative to the advertised capability being false advertising, though acceptable if genuinely still WIP/unshipped.**
- Malformed LSP framing: partial header parsing is line-based and tolerant (skips unknown headers), but `content_length: None` after the header loop just `continue`s (lsp.rs:32-34) without consuming a body — if a client sends a headerless/malformed frame, this could desync the stream and hang forever misinterpreting subsequent bytes as headers. No test coverage (no `crates/cli/tests/` file touches lsp.rs at all).
- Malformed JSON body: silently ignored via `let Ok(msg) = ... else { continue }` (lsp.rs:41-43) — a notification, fine; but if it was actually a request (had an `id`), the client gets no response and hangs. Same pattern as above.

## 7. schema.rs — confirmed schema drift risk
The exported JSON Schema (schema.rs:5-69) is **hand-written and not derived from `ComponentEntry`/`ExtractionOutput`'s actual serde output** (no `schemars` derive, no round-trip test against real serde). Concrete drift already present today:
- `ComponentEntry` (core/src/types/output.rs:47-68) serializes `methods` and `tags` fields (camelCase: `methods`, `tags`) — **neither appears in the hand-written schema's `components.additionalProperties.properties`** (schema.rs:17-41). Since the schema has no `additionalProperties: false`, real output validates fine, but the schema is silently incomplete/stale documentation.
- `ExtractionStats` (core/src/types/output.rs:609-619) has 9 fields (`components_extracted`, `components_skipped`, `files_parsed`, `dts_files_parsed`, `dts_cache_hits`, `duration_ms`, `tier1_count`, `tier3_count`, `opaque_count`) — the schema's `stats.properties` (schema.rs:58-67) only documents 4 of them (`componentsExtracted`, `filesParsed`, `dtsCacheHits`, `durationMs`); `componentsSkipped`, `dtsFilesParsed`, `tier1Count`, `tier3Count`, `opaqueCount` are entirely undocumented.
- `Diagnostic` (core/src/types/diagnostic.rs:8-16) has `line`, `column`, `help` fields — none appear in the schema's diagnostics item properties (schema.rs:45-56), only `severity`/`message`/`file`/`code`.
- The only test (schema.rs:80-82, `test_cmd_schema_valid_json`) just asserts the function returns `Ok` — it never validates against a real `ExtractionOutput` instance or diffs field sets against the struct definitions. **This will silently drift further on every future field addition to core's output types. Medium-high severity — recommend either generating the schema via `schemars` derive on the real types, or adding a test that serializes a real `ExtractionOutput` and validates it exhaustively against the hand-written schema (catches missing-from-schema fields, not just malformed schema JSON).**

## 8. NAPI binding (crates/binding/src/lib.rs)
- `extract_all`, `extract_file_incremental`, `initialize_session` all wrap the actual pipeline call in `tokio::task::spawn_blocking` (lines 121-127, 159-166, 182-189) — a panic inside the closure becomes a `JoinError` via `.await`, which is mapped to `napi::Error::from_reason` rather than unwinding across the FFI boundary directly. This is the correct pattern and should prevent a Rust panic from crashing the Node process for these three entry points.
- `create_session` (line 132-138) and `close_session` (line 193-195) run **synchronously on the calling (JS) thread, not inside spawn_blocking**. `create_session` calls `WatchSession::new(pipeline_options)` directly — if that panics (e.g. from an `unwrap()`/`expect()`/index-out-of-bounds somewhere reachable from `WatchSession::new`, which I did not audit — out of this crate's scope), the panic would occur directly on the N-API-invoked thread. Whether this crashes the Node process or is caught depends on whether napi-rs's `#[napi]` macro auto-wraps function bodies in `catch_unwind` — **I did not verify this in the napi-rs version pinned in Cargo.toml; this needs an explicit check** (grep the napi-rs source/docs for "catch_unwind" behavior in the codegen, or write a deliberate panic test). **Flagging as unverified/high-risk rather than confirmed** — recommend the pipeline team check this specifically since it's the one asymmetry between the async (protected) and sync (unprotected) NAPI functions.
- Error surfaced to Node: all error paths convert to `napi::Error::from_reason(String)` (consistently, every function) — Node callers get a proper JS `Error` with a message, not an opaque crash, for every explicitly-handled error case. Good.
- Thread-safety of shared state: `SESSIONS` is a `DashMap<u32, Arc<WatchSession>>` behind a `LazyLock` (lines 14-15) — appropriately concurrent-safe. `next_session_id` (lines 17-22) combines PID + an atomic counter into a `u32`; the counter is only 16 bits before masking (`counter & 0xFFFF`), so **after 65,536 sessions in one process it silently wraps and can collide with an existing still-open session ID** (a long-lived Vite dev server creating/closing many sessions over a dev session could theoretically hit this, though 65k sessions in one process is an unlikely real-world count). Low severity, untested, noted for completeness.
- forbid(unsafe_code) is only declared in `crates/cli/src/main.rs:1`, not in `crates/binding` — binding crate has no such lint gate (reasonable, since NAPI itself requires FFI, but worth noting the safety-net that exists in CLI doesn't extend here).

- One near-miss: `lsp.rs:36` does `vec![0u8; len]` where `len` comes directly from unvalidated client input (`Content-Length` header, parsed via `.parse().ok()` so at least it's not a panic on non-numeric input) — an attacker-controlled or buggy LSP client could send an enormous `Content-Length` (e.g. `Content-Length: 999999999999`) causing an attempted huge allocation. `usize::parse` would succeed for very large values, and `vec![0u8; len]` would either panic (allocation failure — Rust's global allocator on OOM typically aborts, not a catchable panic) or hang the process attempting a giant allocation. **This is the most concrete un-tested crash risk found in this audit — no upper bound is enforced on `Content-Length` before allocating.** Medium-high severity given it's remotely triggerable if the LSP is ever exposed over anything other than a fully-trusted local stdio pipe (currently stdio-only, so risk is bounded to a malicious/buggy local IDE plugin, but still worth a sanity cap, e.g. reject anything over a few MB).
